# 내 드래곤 데이터베이스 구축안

갱신일: 2026-09-26. **DM-01-C 초안·비공개 자산·개인 정체성의 SQL과 클라이언트 코드를 작성했지만, 신규 테이블·정책은 아직 운영 DB에 적용하지 않았습니다.** [`DM-01-C 마이그레이션`](../supabase/migrations/20260926120000_dm01_cloud_storage.sql)을 검토 대상으로 사용합니다. 성장본·원본 파생 관계와 후속 스토리 기록은 이후 단계입니다.

## 1. 결론

현재 사용하는 Supabase를 유지합니다. 계정은 Auth, 이름·이야기·성장 기록은 PostgreSQL, 그림 파일은 Storage가 담당합니다. 사진을 DB 본문에 직접 넣지 않고 파일의 경로와 소유자·버전을 DB에 기록합니다. 모든 기록은 변경되지 않는 드래곤 UUID로 연결합니다.

핵심은 **공유 게임 도감과 내 드래곤의 비공개 정보**, 그리고 **처음 그린 원본과 나중에 만든 이미지**를 분리하는 것입니다. AI를 사용하지 않아도 원본 그림으로 모험을 시작할 수 있어야 합니다.

## 2. 현재 코드와 확인되지 않은 부분

로컬 SQL과 코드에는 `dragons`, `owned_dragons`, `user_stories`, `ugc_story_progress`, `create_personal_dragon` RPC가 있습니다. 그러나 파일 존재만으로 실제 DB 적용을 보장하지 않습니다.

- `dragons`의 조회 정책은 로그인 사용자 전체에 열려 있습니다. 비공개 성격·만남·개인 이야기를 이 테이블에 계속 추가하지 않습니다.
- `dragon-images`는 SQL상 공개 버킷입니다. 공개 URL을 아는 사람이 그림을 볼 수 있으므로 원본·초안 보관용으로 적절하지 않습니다. Supabase의 공개 버킷은 파일 조회 시 접근 제어를 우회합니다. [공식 버킷 설명](https://supabase.com/docs/guides/storage/buckets/fundamentals)
- 개인 드래곤 생성 RPC는 드래곤과 소유 행을 함께 생성하지만 요청 ID 기반 중복 방지가 없습니다. 능력치도 클라이언트 값을 제한된 범위에서 받으므로 서버 결정 방식이 필요합니다.
- 창작 이야기 진행은 현재 사용자·스토리 단위입니다. 드래곤별·스토리 버전별 진행은 별도 설계가 필요합니다. 기존 1권 챕터 저장과 창작 이야기 저장은 다른 경로입니다.

근거 SQL과 코드: [현재 기준선](DM-00_BASELINE.md#저장-구조-점검과-다음-단계의-제약).

## 3. 제안 데이터 모델

기존 테이블을 무조건 교체하지 않고 새 구조를 단계적으로 연결합니다. 아래 새 이름은 설계 단계의 가칭입니다.

| 영역 | 테이블/서비스 | 저장 내용과 제약 |
| --- | --- | --- |
| 계정 | 기존 Auth / `profiles` | 인증 사용자 UUID, 게임 표시 이름. 비밀번호를 게임 테이블에 저장하지 않음 |
| 공용 도감·소유 | 기존 `dragons` / `owned_dragons` | 공개 가능한 카드 정보와 소유 관계. 개인 비공개 정보를 도감에서 분리 |
| 제작 초안 | 신규 `dragon_drafts` | 소유자, 이름·원소·성격·목표, 제작 단계, 수정 버전. 아직 드래곤이 없어도 저장 가능 |
| 개인 정체성 | 신규 `personal_dragon_profiles` | 영구 dragon_id, owner_id, 첫 만남, 성격, 성장 목표, 보존할 외형 특징, 현재 선택 자산 ID |
| 이미지 이력 | 신규 `dragon_assets` + Storage | 원본/정돈본/성장본 구분, 버킷·파일 경로, 소유자, draft_id 또는 dragon_id, 원본 자산 ID, MIME·크기·체크섬 |
| 이야기 버전 | 신규 `story_versions` | 원작 각색/사용자 창작 출처 구분, story_id, 변경 불가능한 장면 스냅샷과 버전 |
| 모험 진행 | 신규 `story_runs` | 사용자·드래곤·스토리 버전에 연결된 진행 회차와 현재 장면. 활성 회차 중복 방지, 수정 버전으로 동시 저장 충돌 감지 |
| 기억·성장 | 신규 `story_events` / `growth_events` | 선택·교감·성장 사건, 발생 시각, 관련 장면/모험/이미지. 서버가 검증한 보상만 지급 |
| AI 처리 | 신규 `image_jobs` | 요청 UUID, 입력 자산, 대기/처리/완료/실패, 결과 자산, 재시도 횟수. API 키는 저장하지 않음 |

대표 관계는 `사용자 → 내 드래곤 → 이미지 이력 / 모험 회차 / 성장 기록`입니다. 이야기 본문 버전은 여러 모험이 참조할 수 있지만, 선택과 성장 기록은 각 드래곤·회차에 속합니다.

### 반드시 필요한 제약

- 소유자·드래곤·자산 연결을 외래 키로 검증합니다. 현재 선택 이미지가 다른 사용자의 이미지가 되지 않도록 `(owner_id, dragon_id, asset_id)` 관계까지 검사합니다.
- 이미지 원본은 덮어쓰지 않습니다. 정돈·성장 이미지는 새 자산으로 만들고 `source_asset_id`로 이전 모습을 추적합니다.
- 보상은 `(사용자, 드래곤, 보상 규칙, 보상 주기/해당 사건)`의 고유 키로 중복 지급을 막습니다. 새 회차를 시작했다고 1회성 보상이 다시 지급되지 않아야 합니다.
- 제작 확정 요청 UUID는 소유자와 함께 유일하게 저장합니다. 같은 요청 재전송은 기존 결과를 돌려주고 드래곤을 중복 생성하지 않습니다.
- 자주 조회하는 소유자·드래곤·스토리 버전·발생 시각에 인덱스를 둡니다. 삭제 보존 기간·내보내기 정책은 출시 전에 확정합니다.

## 4. 손그림 업로드부터 성장까지

1. 제작 시작 시 비공개 초안을 저장합니다. 입력을 수정할 때 초안 버전을 확인하며 자동 저장합니다.
2. 촬영·업로드한 파일은 형식·실제 파일 내용·용량을 검증하고, 위치 등 불필요한 사진 메타데이터를 제거한 보관본을 만듭니다. 원래 그림 내용은 유지합니다.
3. 새 비공개 버킷(예: `dragon-originals`)의 사용자별 경로에 원본을 업로드합니다. DB에는 파일 경로를 저장하며, 일시적인 서명 URL을 영구 저장하지 않습니다.
4. 원하면 AI 작업을 요청합니다. 원본은 그대로 두고 결과를 별도 저장합니다. 실패하면 원본 사용 또는 재시도가 가능합니다. 생성 비용·횟수 제한은 서버에서 적용합니다.
5. 사용자가 그림을 선택하고 확정하면 서버 RPC가 소유자·파일 존재·상태를 검증한 뒤 드래곤·소유권·개인 설정을 DB 트랜잭션으로 생성합니다. 시작 능력치는 서버 규칙으로 결정합니다.
6. 첫 만남과 1권 모험은 같은 드래곤 UUID로 진행합니다. 선택이 기억으로 누적되고, 성장 시 새 이미지가 앨범에 추가됩니다. AI 이미지 생성 없이도 성장은 진행됩니다.

Storage 파일 업로드와 DB 트랜잭션은 하나의 원자적 작업이 아닙니다. 따라서 `업로드 대기 → 파일 업로드 → 확정` 상태를 분리하고, 응답 유실 후에는 요청 UUID로 결과를 먼저 조회합니다. 미사용 파일은 유예 기간·소유자·참조 여부를 확인한 정리 작업으로만 제거합니다.

현재 공개 버킷을 즉시 비공개로 바꾸면 기존 카드 URL이 깨질 수 있습니다. 기존 파일은 호환성을 유지하고 새 원본부터 비공개로 저장합니다. 공개는 사용자가 선택한 카드용 복사본만 대상으로 하며, 비공개 파일은 인증 다운로드 또는 짧은 유효기간의 서명 URL로 제공합니다. [Storage 접근 방식](https://supabase.com/docs/guides/storage/buckets/fundamentals)

## 5. 권한과 서버 책임

- 개인 초안·이미지 메타데이터·진행·기억에는 본인만 읽고 수정할 수 있는 RLS를 적용합니다. 테이블 권한과 RLS를 함께 검토합니다. [공식 RLS 설명](https://supabase.com/docs/guides/database/postgres/row-level-security)
- 서버는 로그인 토큰의 사용자 ID를 사용합니다. 클라이언트가 보낸 owner_id, 경험치, 보상량을 신뢰하지 않습니다.
- 성장·재화·소유권의 중요한 변경은 검증된 서버/RPC만 수행하도록 직접 쓰기 권한을 제한합니다. 본인 행에 대한 RLS만으로 게임 부정행위가 방지되지는 않습니다.
- 관리자 키는 서버 또는 승인된 테스트 프로세스에만 둡니다. `VITE_` 변수·브라우저 번들·README·로그·채팅에 넣지 않습니다.
- 실제 사용자 그림과 이야기 내용을 진단 로그에 남기지 않습니다. 공개 공유는 기본 비공개와 명시적인 공개 선택을 전제로 별도 검토합니다.

## 6. 구축 순서

1. **DM-00 관리 접근 및 실측:** 현재 키의 Auth·DB 연결은 HTTP 200으로 확인했습니다. 테스트용 관리 인증을 준비하고, 실제 테이블·RLS·버킷·적용 마이그레이션을 읽기 전용으로 조사합니다. 백업과 복구 수단도 확인합니다.
2. **별도 개발 환경:** 운영과 분리된 개발 프로젝트 또는 로컬 Supabase에서 스키마를 검증합니다. 현재 로컬에는 Supabase CLI/Docker/psql이 확인되지 않았으며 설치·새 환경 생성은 별도 작업입니다.
3. **DM-01 최소 구조:** 초안 → 비공개 자산 → 개인 정체성 → 중복 방지 생성 RPC 순서로 추가합니다. 기존 화면은 새 데이터가 없으면 기존 데이터로 표시하도록 호환성을 유지합니다.
4. **DM-02 이야기 연결:** 이야기 버전·드래곤별 진행·첫 성장 사건을 추가합니다. 기존 기록의 영구 드래곤 UUID 매핑을 검증한 뒤 이전합니다.
5. **DM-03/04 확장:** 질문형 창작, 기억·앨범, AI 작업 큐를 추가합니다. DM-05의 전투 능력·보상 정합성은 별도 서버 검증을 동반합니다.
6. **배포:** 실제 원격 상태와 로컬 이력을 대조한 뒤 필요한 추가 마이그레이션만 리뷰·승인·적용합니다. 현재 저장소의 SQL 전체를 검토 없이 `db push`하지 않습니다. [마이그레이션 관리](https://supabase.com/docs/guides/local-development/database-migrations)

## 7. 실제 저장 검증 상태와 실행법

사용자는 현재 연결 DB에서 **새 테스트 계정·그림·드래곤 생성 및 해당 데이터 정리**를 허용했습니다. 기존 플레이어 데이터·운영 설정 변경, 유료 AI 호출은 범위 밖입니다.

2026-09-26 확인 결과:

- 로컬 설정 대상: `mcwafbwjpkjtvqfenqys`.
- **이전 진단 정정:** `/rest/v1/` 스키마 요청만 HTTP 401(`Invalid API key`)을 반환했습니다. 같은 키로 `/auth/v1/settings`와 `/rest/v1/dragons?select=id&limit=0`는 모두 HTTP 200입니다. 따라서 이 401을 키 무효나 전체 DB 연결 실패의 증거로 보지 않습니다. 점검 도구를 실제 Auth·테이블 경로로 변경했으며, 키·DB 권한·운영 설정은 바꾸지 않았습니다.
- 로컬 서버·브라우저 키/URL은 서로 일치하고, 레거시 키의 프로젝트 식별자와 만료 시간도 일치/유효합니다. JWT 내용 확인만으로 서명 유효성을 보장하지 않으며, 위 API 응답으로 실제 수용 여부를 구분했습니다.
- 관리 페이지는 로그인 화면이며 로컬 관리자 키·전용 테스트 계정이 없습니다. 로그인 승인과 실제 인증 수단은 별개입니다.
- 쓰기 검증은 관리자 키 누락 검사에서 중단했습니다. **원격 테스트 데이터 생성·삭제, 스키마 변경, 유료 AI 호출은 수행하지 않았습니다.**

```sh
# 읽기 전용: Auth 설정 및 dragons 0행 조회. 사용자 행 반환/RPC 실행 없음
npm run check:database

# 아래 명령은 서버 전용 테스트 자격 증명 준비 후에만 실행
# 테스트 계정 2개·합성 PNG·드래곤·비공개 창작 이야기/진행을 생성하고 정리함
npm run test:storage -- --project=mcwafbwjpkjtvqfenqys
```

로컬 자격 증명은 Git에서 제외되는 `.env.development.local` 또는 프로세스 환경 변수에 둡니다. `SUPABASE_SERVICE_ROLE_KEY`는 계정 생성·정리 전용이며, 실제 업로드·생성·조회 검사는 테스트 사용자의 일반 인증으로 수행합니다. 권한이 과도한 관리자 키를 제공하기 어렵다면 동일한 검증·정리 절차를 승인된 관리 환경에서 실행하도록 전환합니다.

새 [저장 검증 스크립트](../scripts/verify-storage.mjs)는 업로드 → 개인 생성 RPC → 소유 확인 → 진행 저장 → 새 클라이언트 재로그인 → 이미지 바이트/진행 확인 → 다른 계정 접근 차단 → 테스트 데이터 정리 순서입니다. 고유 실행 표식과 새 테스트 소유자 ID로만 정리합니다. 응답 유실로 계정 생성 여부가 불확실하거나 정리가 실패하면 실행 표식을 출력하고 완료로 처리하지 않습니다. 강제 종료·네트워크 단절 후에는 해당 표식의 테스트 잔여물을 확인해야 합니다.

기존 `test:ownership`은 운영 설정을 바꾸는 동작을 포함하므로 이번 범위에서는 실행하지 않습니다. 새 스크립트는 실제 읽기 전용 연결까지 통과했으며 쓰기·정리 경로는 아직 실행하지 않았습니다. 안전장치 5개와 연결 진단 회귀 7개 테스트는 실제 저장 성공의 증거가 아닙니다. Auth 설정/0행 조회는 로그인 사용자 데이터의 저장·조회 권한이나 RPC의 배포 여부를 입증하지 않습니다.
